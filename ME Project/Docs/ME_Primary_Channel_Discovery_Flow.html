ME Primary × Secondary · CAN-FD interface

How the Primary Finds Your Channels

At power-up the Primary asks every Secondary which of its channels physically exist, then registers only those with the Web Application. This is the complete start-up sequence.

Status proposed — not yet implemented Date 27 Aug 2026 Protocol Master-Slave CAN V1.0

For the Secondary board team: sections 01, 04 and 05 are your interface contract — what arrives on your bus and what you must send back. Sections 02 and 03 show where your reply ends up, and section 06 is Primary-side detail; neither changes what you implement.

The start-up sequence in one line: ask every Secondary which channels exist over CAN-FD (01–02) → write the answers into a channel map → register only the present ones with the Web Application over TCP (03) → run.

01

The exchange

The Primary probes one block at a time and waits for each answer before moving on. There is never more than one outstanding request on the bus.

02

Discovery, step by step

The same sweep as a decision path. Nothing is registered with the Web Application until every Secondary has been asked.

03

Registering with the Web Application

The channel map now holds a verdict for all 64 possible circuits. The Primary opens one TCP connection and sends one 0xDD frame per present channel. Absent channels are never offered — that is the whole point of the sweep.

The part that is easy to misread — there are two different retries

They look similar but fire in different situations, and only one of them reconnects. Which one applies to a rejected channel depends entirely on whether any other channel got in.

If the server echoes back a different DeviceID or CircuitID than was sent, that is logged as informational only and the registration still succeeds. Only the Value byte decides whether a channel is admitted.

Each channel becomes a CircuitID — one byte, upper nibble the Secondary, lower nibble the channel, both counting from 1. That byte identifies the circuit in every frame from here on.

Why 0x02 counts as success

Both 0x01 (Registered) and 0x02 (Already Registered) mean the channel is registered — 0x02 only adds that the Web Application already held a record for it, which is the normal answer after a reconnect. Only 0x00 is a rejection.

This is not a hypothetical distinction. Treating 0x02 as a failure once made the board close the connection and re-register every 30 seconds, observed on hardware.

Both blocks of a Secondary share one CAN identifier, so the identifier alone cannot say which four channels are being asked about. The Channel # field in the request carries it.

Action for the Secondary team

Read byte 9 of the request to decide which block to answer. Everything else in the probe is zero — it carries no setpoint and commands nothing. Reply on function 0x02, as with any READ_VALUES.

This rule is not in the Master-Slave CAN V1.0 workbook — the workbook never says how a Secondary distinguishes a Block 1 request from a Block 2 request. If your firmware already resolves this a different way, tell us before we build it, because the Primary has to match.

05

How presence is decided

Per channel, from its own 16-byte slot in the reply. The test is whether the slot carries anything at all — not whether the voltage is non-zero.

Channel 2 PRESENT

Fitted, idle, nothing connected to its terminals. Reads 0.000 V — and is still present.

Question for the Secondary team

The rule above is an assumption we need you to confirm. It reads: if all 16 bytes of a channel's slot are zero, that channel is not fitted.

Two things would break it. If your firmware zero-fills the slots of channels it does not have and a fitted channel can genuinely report 0.000 V with Channel # also zero, then nothing in the frame separates the two cases. And if a fitted channel's slot can be all-zero for any other reason, the Primary will skip a working channel silently. Please tell us what your firmware actually puts in the slot of a channel that is not fitted.

06

Primary-side internals

Three existing behaviours in the Primary's CAN driver that this sweep is the first thing to exercise. Listed for completeness — none of them changes anything on the Secondary side.

INTERNAL · 1

The Primary hears its own probe

The M7 co-processor loops every transmitted frame back on the same receive stream that carries real replies. The sweep must compare each inbound frame against the probe it just sent and discard the match, or its own probe would read as four present channels.

INTERNAL · 2

Block identity is tracked, not inferred

The driver normally guesses which block a reply belongs to from which channels are already active — safe only while no Secondary has channels in both blocks. The sweep probes both blocks back to back, so it tracks the block it is probing explicitly.

INTERNAL · 3

Probes bypass the transmit buffer

Outgoing frames normally go through a shared buffer so one channel's setpoint cannot overwrite another's. A probe carries no setpoint, and passing it through that buffer would erase the Channel # bytes that select the block — so probes are sent directly.
