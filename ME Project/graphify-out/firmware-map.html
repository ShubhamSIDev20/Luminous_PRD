01 System context

Three parties talk to each other. Only one link is physically real today.

02 What happens, in order

  1. 1

    Boot

    main() parses CLI args, applies config defaults (sys_init.c), allocates the four message queues at file scope (app_queues.c — each is ~1 MB, too big for a thread stack, so it's a hard rule they're never local), spawns the four threads below, then blocks until SIGINT/SIGTERM.

  2. 2

    Registration

    comm_thread opens a TCP connection to the Web Application and retries with capped exponential backoff until a 0xDD registration frame is acknowledged. Success marks the circuit in circuit_registry and fires post_reg once — a single 0xCC telemetry frame over UDP, before any program exists, so the Web App has live data immediately.

  3. 3

    Frame routing & admission

    Every inbound TCP byte run goes through frame_router: classify by start byte, resolve the true length (declared length first, CRC as a backstop if the length table is wrong — ADR-19), then gate on circuit_registry. An unregistered circuit's frames are dropped before they ever reach a queue. What survives is ack'd immediately, then handed to g_q_core (control, 0xEE) or g_q_data (config/battery/program, 0xAA/0xBB).

  4. 4

    Config, battery & program storage

    data_mgr owns circuit_store: the 40-byte battery record (12 fields, including two IEEE-754 floats) and the raw program bytes uploaded in chunks and terminated by the 0xAA55 chain marker. It answers the Web App directly, and answers core_logic's internal requests for "give me the stored program" the same way.

  5. 5

    Control commands & step execution — the newest, most-changed part

    A 0xEE Start command reaches me_execute_program() in core_logic, which fetches the stored program, walks it with program_chain, and decodes each step's operator (SET / CCChg / STOP) with step_decode. From there a per-circuit step_engine state machine takes over: enter step → advance time → check cutoffs (time/current/voltage) → emit a CAN setpoint or poll → repeat until the chain's terminator. This replaced the old 1 Hz synthetic ramp (demo_realtime.c, deleted session #10) with the real thing.

  6. 6

    CAN-FD exchange — simulated

    step_engine's output goes to can_mgr as a SET_VALUES/READ_VALUES request packed by can_frame (little-endian floats — deliberately the opposite byte order from the Web App's wire format). can_mgr has no physical CAN transceiver behind it yet, so it fabricates a plausible feedback value and sends it back. Three missed responses in a row would mark a channel offline — that path is tested but has never fired against real hardware.

  7. 7

    Telemetry

    Each tick, core_logic also pushes a 0xCC realtime frame (current, voltage, digital I/O) to comm_thread for UDP delivery to the Web App at roughly 1 Hz, ending with an idle frame when a circuit stops.

03 Internal architecture

Four threads, four in-process queues, zero shared mutable state outside them. Every queue send carries a finite timeout and drops on expiry — deadlock is impossible by construction, not by convention.

04 Protocol frame groups

Every frame on the TCP link is CRC-16/Modbus checked, big-endian on the wire. The CAN-FD side (simulated) uses little-endian floats — a deliberate, easy-to-forget mismatch.
