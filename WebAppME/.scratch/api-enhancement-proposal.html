Executive Summary

This proposal addresses two critical gaps in the BatteryTestingSystem REST API that affect developer experience and API ergonomics:

1. Missing DBC Files Endpoint

Current state: Programs and batteries can be listed programmatically, but DBC files cannot be discovered via the API.

Impact: MCP tools and external clients must rely on battery-specific lookups or manual knowledge of DBC IDs.

2. Repetitive Channel Requests

Current state: To operate on channels 1-64, API clients must construct 64 identical request objects in an array.

Impact: Verbose payloads, error-prone construction, poor developer experience when working with bulk operations.

Problem Statement

Missing DBC Files Endpoint

What exists:

  • POST /api/Device/GetPrograms ✅ Lists all test programs
  • POST /api/Device/GetBatteries ✅ Lists all battery configurations
  • POST /api/Device/GetDbcFiles ❌ Does not exist

Developer pain point: When using MCP tools or building external integrations, there's no way to discover available DBC files. The IDbcService interface has:

  • GetByBatteryIdAsync(long batteryId) - requires knowing a battery ID first
  • GetByIdAsync(long id) - requires knowing the DBC ID already
  • No GetAllAsync() equivalent for listing all DBC files

Repetitive Bulk Channel Operations

Current API pattern: To send a program to channels 1-64 requires:

{
  "requests": [
    {"DeviceID": 1, "ChannelNumber": 1, "ProgramId": 5, "BatteryId": 3, "dbcId": 2},
    {"DeviceID": 1, "ChannelNumber": 2, "ProgramId": 5, "BatteryId": 3, "dbcId": 2},
    {"DeviceID": 1, "ChannelNumber": 3, "ProgramId": 5, "BatteryId": 3, "dbcId": 2},
    // ... 61 more identical objects
  ]
}

Pain points:

  • Large payloads: 64 channels = 64 nearly-identical objects
  • Error-prone: Manual construction of arrays, easy to make mistakes
  • Poor UX: MCP tool must generate repetitive structures
  • Network waste: Unnecessary bandwidth for duplicate data

Proposed Solutions

Enhancement 1: Add DBC Files Listing

New Endpoint

Add a GetDbcFiles endpoint following the existing pattern for Programs and Batteries:

POST /api/Device/GetDbcFiles

Response structure:

{
  "success": true,
  "data": [
    {
      "dbcFileRecordId": 1,
      "fileName": "Tesla_Model3_BMS.dbc",
      "description": "Tesla Model 3 Battery Management System",
      "batteryId": 3,
      "batteryName": "Li-ion",
      "uploadedBy": "admin",
      "uploadedAt": "2026-01-15T10:30:00Z"
    }
  ],
  "message": "success!"
}

Implementation points:

  1. Add GetAllAsync() to IDbcService interface
  2. Implement in DbcService and DbcRepository
  3. Add controller endpoint in DeviceController
  4. Add MCP tool in DeviceMcpTools

Enhancement 2: Channel Range/List Support

Backward Compatible

Design approach: Enhance the existing CommonRequest model with optional channel expansion fields.

public class CommonRequest
{
    public int DeviceID { get; set; }
    public int SecondaryBoardNumber { get; set; } = 1;
    public int ChannelNumber { get; set; }  // Existing (backward compatible)

    // NEW: Range notation (e.g., "1-64" or "1-8,17-24")
    public string? ChannelRange { get; set; }

    // NEW: Explicit list (e.g., [1,2,5,10])
    public List<int>? ChannelList { get; set; }

    public int? ProgramId { get; set; }
    public int? BatteryId { get; set; }
    public int? dbcId { get; set; } = 0;
}
Priority resolution:
  1. If ChannelList is provided → expand to those specific channels
  2. Else if ChannelRange is provided → parse range notation and expand
  3. Else use single ChannelNumber (existing behavior, fully backward compatible)

Usage Patterns

Single Channel (Existing Behavior)

{"DeviceID": 1, "ChannelNumber": 5, "ProgramId": 10}

Range Notation

// All channels 1-64
{"DeviceID": 1, "ChannelRange": "1-64", "ProgramId": 10}

// Multiple ranges
{"DeviceID": 1, "ChannelRange": "1-8,17-24,33-40", "ProgramId": 10}

Explicit List

{"DeviceID": 1, "ChannelList": [1, 2, 5, 10, 15, 20], "ProgramId": 10}

Mixed Requests (Multiple Devices/Programs)

[
  {"DeviceID": 1, "ChannelRange": "1-32", "ProgramId": 10, "BatteryId": 3},
  {"DeviceID": 1, "ChannelRange": "33-64", "ProgramId": 20, "BatteryId": 5}
]

Implementation Plan

Phase 1: DBC Files Endpoint ⏱️ 2 hours

Low Risk No breaking changes, straightforward addition

  • Add GetAllAsync() to IDbcService
  • Implement in DbcService.cs
  • Add GetDbcFiles endpoint in DeviceController.cs
  • Add GetDbcFiles tool in DeviceMcpTools.cs
Phase 2: Channel Range Support ⏱️ 4-6 hours

Medium Risk Backward compatible, requires careful expansion logic

  • Add ChannelRange and ChannelList to CommonRequest
  • Create ChannelExpander utility with range parsing
  • Update controller endpoints to expand requests before processing
  • Validate expansion limits (max 128 channels per request)
Phase 3: MCP Tools Update ⏱️ 2 hours

Low Risk Update tool signatures and descriptions

  • Update MCP tool parameters to accept channelRange and channelList
  • Update tool descriptions with usage examples
  • Test with Claude Desktop integration
Phase 4: Testing & Documentation ⏱️ 3-4 hours

Medium Effort Comprehensive validation

  • Unit tests for ChannelExpander range parsing
  • Integration tests with 64-channel simulator
  • Backward compatibility validation
  • API documentation updates

Migration Path

Zero Breaking Changes

Both enhancements are fully backward compatible:

Existing Pattern Still Works? Notes
Single ChannelNumber ✅ Yes Existing behavior unchanged
Array of CommonRequest ✅ Yes Each request processed individually
No DBC endpoint calls ✅ Yes New endpoint is additive

Adoption strategy: Existing clients continue working without changes. New clients and MCP tools can adopt enhanced patterns immediately for better ergonomics.
