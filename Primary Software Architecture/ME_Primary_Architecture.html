ME Battery Testing System · Annex A2 · Software Architecture

One line separates work that has a deadline from work that does not.

The Primary Board is the only part of the system that knows what a test program means. It runs 64 test programs at the same time, on a general-purpose operating system, and keeps every circuit inside its limits while a lab PC reboots, a network drops, or a power stage stops answering.

One boundary, and everything follows from it

On a microcontroller you get real-time behaviour partly by default: there is no heap, no scheduler you did not write, and no page cache. On Linux none of that is true. Code that quietly breaks timing still runs, and usually still passes testing.

So the software is split into two domains with different rules. Below the line, work has to finish before the next measurement update arrives, for all 64 circuits: memory is allocated once at startup and locked in RAM, priority is high, and there is no filesystem and no network. Above the line, work just has to make progress. The two sides are joined by fixed-size queues, and real-time code never waits for best-effort code.

One pass per measurement update, for every circuit

Samples arrive and immediately split two ways. The execution engine uses them to decide whether the current step has finished. The safety supervisor uses the same samples, at the same moment, to check the circuit is still inside its configured limits — and it reaches the dispatcher without going through the engine.

How often measurements arrive is not yet decided (Q-62). Nothing in this architecture depends on a specific rate; the load figures further down are written as formulas so they can be filled in once the DC-DC board design settles it.

Three checks, in three components, on purpose

A setpoint only reaches the hardware after passing three checks. They live in different components so that one bug cannot get past all three, and each one catches a different kind of mistake.

NoteFR-PRI-189AA

The dispatcher clamps every setpoint, every time, whatever sent it. The conversion happened on a different machine, in different code. A wrong nominal capacity turns 10 ACn5 into a large current that still looks reasonable. And the clamp is the only check a conversion bug cannot get past.

The three boundary rules

RuleWhy
Queues have a fixed size, both directions Allocated at startup. An unbounded queue keeps growing until memory runs out.
Real-time code never waits for best-effort code If a queue is full, the real-time side applies its overflow policy and carries on. If it waited, a slow disk write could delay a limit check.
Nothing needed mid-step is on the other side A program is loaded into its context when the circuit starts; the engine fetches nothing after that. This is what makes “a test keeps running if the operator PC reboots” true by design rather than by hope.

One operator breaks the third rule. SAVE and REST read and write named test sections stored in the Web Application’s database, and the manual says that if the data is missing the running program waits or is interrupted. So either the Durable Store takes over saved sections, or a program using REST cannot start while the link is down. Tracked as Q-51 — a structural question, not an implementation detail.

RecoveryFR-PRI-216
FR-PRI-374, -424

Nothing restarts itself

After a power loss, a board reconnecting, or a watchdog reset, the Primary does not know the state of the pack — whether it self-discharged, whether someone moved something, or whether the outage was caused by a fault in the first place. So it restores the context, reports it along with how long the outage was, and waits for a person. FAULT stays set until someone acknowledges it.

Putting 40 A back into a pack in an unknown state without a person deciding is not defensible. If unattended multi-week testing makes waiting impractical, the answer is a conditional resume with clear bounds: allowed only if the outage was shorter than a configured limit, the pack voltage on restart is within a configured band of what it was before, and no fault was latched. That would be an opt-in per circuit, never the default.

Load at 64 circuits

Load scales directly with the measurement update rate, which is not yet decided (Q-62). The table uses R = updates per second per circuit, so the figures can be filled in once R is fixed. The example column is illustrative only.

LoadFormulaExample at R = 10
Limit-evaluation passes64 × R per second640 / s
CAN-FD 1, one frame per channel64 × R frames/s640 frames/s · ~12 % of the bus
CAN-FD 1, aggregated per board24 × R frames/s240 frames/s · ~8 %
Registration dataindependent of R — set by the program’s triggers~500 MB/day at 1 record/s/circuit

Two conclusions hold at any rate. Aggregate measurements per board rather than sending one frame per channel — with 8 channels per board that cuts frame count by roughly two-thirds, and the saving that matters is interrupt and processing load on the Primary, not bus bandwidth. And size receive queues for bursts, not averages: if all 8 boards report at the same moment, 24 frames arrive back to back, and releasing a SYNCLine barrier can put 64 circuits into a new step at once.

Load must be measured on target hardware at the full 64-circuit configuration. A test at a reduced circuit count is not evidence.

What the Primary does not do, on purpose

Not in the PrimaryWhere instead, and why
The current and voltage regulation loopThe DC-DC board. Regulation belongs next to the hardware, so it does not depend on a CAN link staying up.
Hardware protection of the power stageThe DC-DC board. Protection must not need the Primary to be alive.
Speaking a battery vendor’s BMS protocolThe BMS Interface Board. The Primary only maps decoded signals to a circuit.
Stopping a test on a single-cell conditionNowhere, by decision. Limits cannot use BMS signals, so single-cell protection is handled by the pack’s own BMS and by the safety limits working on pack terminal measurements.
Long-term storage of resultsThe Web Application database. The Primary buffers; it is not the archive.

Open questions that would change this architecture

Listed rather than hidden. These change the structure, not just a number.

IDQuestionWhat it changes
Q-62 How often do the DC-DC boards report measurements? Sets bus load, how accurately the Ah/Wh totals can be integrated, and how finely registration can be triggered. Nothing structural, but every load figure above and the staleness timeouts in Part 02 depend on it. Earlier drafts stated 100 ms; that came from a line in the BM4 manual about Digatron’s own hardware and has been removed. It is our decision to make.
Q-50 The opcode set does not cover every nominal-value combination in the manual — power-plus-voltage, and resistance. Recommend replacing the fixed opcode list with two mode fields — main regulation mode plus transition mode. Covers every combination, includes resistance, and costs nothing before Part 03.
Q-51 SAVE / REST reach into the Web App database, breaking the third boundary rule. Either the Durable Store owns saved sections, or programs using REST cannot start with the link down.
Q-43 Can a parallel group span DC-DC boards? With 8 channels per board, a 16-circuit group has to. Whether the dispatcher has to divide setpoints and combine measurements across boards on a shared time base — considerably harder than within one board.
Q-11 Is unattended multi-week testing required? Whether “nothing restarts itself” gains a conditional resume path.
Q-41 Which kernel configuration — standard, PREEMPT, or PREEMPT_RT? Nothing structural, but adding PREEMPT_RT to a vendor BSP late in a project is a known way to lose a month.
Q-30 Eight in-scope operators are only documented in a manual we do not have. Possibly the dispatcher and the DC-DC interface, if any of them implies a control mode.
