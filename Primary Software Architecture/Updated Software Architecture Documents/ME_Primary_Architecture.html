BLK-01

System Context

What the Primary is connected to, and which way the data flows

Read this as The Primary is the only block that drives anything. IF-2 is its single control interface — setpoints down, measurements up. IF-3 and IF-4 are strictly inbound and never influence a cutoff decision; BMS data is log-only. Everything above the Primary is a user interface and an archive, everything below is a sensor or an actuator.
BLK-02

The Two-Domain Model

The one idea the whole architecture rests on

Why it is built this way A single-priority design works on the bench and fails in the field. The failure mode is specific: an operator exports a 30-day test, the database saturates three cores and the page cache, and a cutoff is evaluated 400 ms late on 64 circuits at once. This split makes that structurally impossible rather than merely unlikely. Losing a display sample is acceptable; missing a cutoff is not — so the boundary always favours the domain above it.

BLK-05

The Control Cycle

The heartbeat. Runs at a fixed period, forever.

The rule that makes it testable All 64 circuits are processed every cycle, in the same order, in one thread — not 64 threads. Sixty-four threads would add scheduling jitter and non-determinism for no throughput gain at this scale. Fixed order means that given the same program and the same measured inputs, you get the same result every run. Without that, no failure can be reproduced and no test result can be defended.

BLK-07

Data Path & Store-and-Forward

How a measurement becomes a permanent record — with or without the Web App

The policy that matters A data-loss condition never stops a test. That is a deliberate choice, not an oversight — a 30-day battery test is far more expensive than a gap in the log. The buffer also never deletes a record the Web App has not confirmed receiving. Still open: whether exhaustion discards oldest or newest. The recommendation is discard-newest, preserving a continuous record from the start of the outage, because a log with a hole in the middle is harder to defend than one that is complete up to a known point.
BLK-08

Fault Path

Nine different triggers, one convergent response

Ordering is the whole point When internal corruption is detected the instinct is to reset immediately. That is wrong here. A reset that leaves the power stage running at 40 A while the controller is absent is worse than the fault that triggered it. Command safe idle first, then restart. The DC-DC board's own 1 s setpoint keep-alive timeout is the backstop if even that fails.
BLK-09

Startup Sequence

Power-on to ready. Note what does not happen.

  1. Platform boot
    Linux and the NXP BSP come up. No login, no shell, no desktop, no display required.
  2. Control application starts automatically
    Unattended, with no operator input. If it ever terminates unexpectedly, the platform restarts it.
  3. All 64 circuits commanded to safe idle
    Within 2 seconds of power-on, before any other function is enabled.
    Safe idle comes first, always. Power never flows as a side effect of initialisation.
  4. Power-on self-test
    Persistent storage · each of the four CAN-FD controllers · each RS-485 transceiver · Ethernet · the real-time clock. Every result is reported; any failure is annunciated as a Fault.
  5. Verify stored configuration and programs by checksum
    Corruption is annunciated — never silently discarded, never silently repaired.
  6. Load persisted execution contexts
    Whatever each circuit was doing when the power went away is read back from durable storage.
  7. Circuits that were running → recovery-pending
    Never directly back to RUNNING.
    A human decides whether to resume. This is also the design's sharpest edge — see the note below.
  8. Report the restart cause
    Power-on, commanded reset, watchdog timeout, or fault. A watchdog restart that happened while a circuit was running is annunciated as a Fault, not quietly resumed.
  9. Enable IF-1 and wait
    The Primary is now ready. It does nothing further until an operator commands it.
Open question — this one has teeth Step 7 means a 20-second power blip at 2 a.m. on day 19 of a 30-day unattended test destroys that test. The FRD asks (Q-11) whether a bounded conditional auto-resume is needed instead — resume only if the outage was under N minutes, the pack voltage on restart is within a band of its pre-outage value, and no fault was latched. That is a real feature needing real safety analysis, not a configuration flag. Someone has to decide.
BLK-10

Three Safety Barriers

What a bad setpoint has to get through to reach a battery

Barrier 1 · Best-Effort · at transfer time
Program Validation
Catches an operator authoring an unsafe or malformed program. Runs once, when the program is received.
PROGRAM STORE · FR-PRI-070s
Barrier 2 · Critical · at every dispatch
Setpoint Clamping
Catches a corrupted program, a defect in the execution engine, and a memory error. Runs on every single setpoint, and annunciates any clamp.
SAFETY SUPERVISOR · FR-PRI-116
Barrier 3 · DC-DC board · always
Hardware Protection
Catches everything above, plus total loss of the CAN link. Does not depend on the Primary being alive or correct.
SECONDARY HARDWARE · NOT SOFTWARE
Barrier 2 is the one people leave out Validation at transfer time only catches programs that were wrong when written. It cannot catch a program that was corrupted afterwards, an engine defect, or a bit-flip in RAM. Clamping every setpoint immediately before transmission costs almost nothing and closes all three. A program can never command outside the safety envelope, no matter how it got corrupted.
E-Stop — separate from all three, and hardware-critical Must reach safe idle within 100 ms, and must be fail-safe: a disconnected, broken, or unpowered E-Stop circuit reads as asserted, not as safe. That means normally-closed, normally-energised wiring. An E-Stop wired active-high fails to danger — cut the wire and the system believes everything is fine. Clearing it requires both the physical input returning to safe and an explicit operator acknowledgement. Software must not be the only path by which an E-Stop removes power — a hardware path independent of Primary firmware is expected (Q-27, unconfirmed).
BLK-11

A53 or M7? — Open Decision

The FRD never says. This is the gap that has to close first.

ME-FRD-02 §2.2A describes the platform as "Quad-core, 4 GB RAM, 32 GB, Linux" and is completely silent on the Cortex-M7. Every real-time requirement is written as a Linux problem. So the FRD does not actually tell anyone where the control path runs.

OPTION A · All control on A53 under Linux + PREEMPT_RT  — recommended
  • One codebase, one language, one debugger.
  • Timing margin is ample — a 10 ms deadline against sub-millisecond latency.
  • CAN, Ethernet and storage all use mature mainline Linux drivers.
  • No inter-core protocol to design, version and debug.
  • Cost: needs PREEMPT_RT in the vendor BSP — confirm early.
  • Cost: the house rules are enforced by review, not by hardware.
OPTION B · Control path on M7, Linux for everything else
  • Hard physical isolation — Linux cannot preempt the control path at all.
  • Survives a Linux crash or OOM event still regulating safely.
  • Cost: two codebases, two toolchains, two debug environments.
  • Cost: must design and version an A53↔M7 protocol over the Messaging Unit.
  • Cost: M7 TCM and RAM are limited — 64 pre-allocated contexts plus buffers need sizing before committing.
  • Cost: a lot more integration work for margin the system does not need.
Recommendation — for architect confirmation, not a decision made here Take Option A as the baseline, and reserve the M7 for a narrow safety role: independent hardware watchdog supervision of the Linux control application, plus a fail-safe path that can command all channels to safe idle if Linux stops responding. That captures the M7's genuine benefit — surviving a Linux failure — without paying for a split control architecture to buy timing margin the system already has in abundance.

Cost of being wrong is low. The Critical Domain is already isolated behind the BLK-02 boundary, so if measured latency later proves inadequate it can be relocated to the M7 without redesigning the Best-Effort side. Confirm PREEMPT_RT availability in the NXP BSP first — retrofitting it late is a well-known way to lose a month.

What this picture is telling you Nothing here requires microsecond determinism. The tightest deadline is 10 ms, and Linux with PREEMPT_RT typically holds worst-case scheduling latency well under a millisecond on this class of SoC — roughly an order of magnitude of headroom. That is the case for Option A in BLK-11. The reason the budget is so relaxed is structural: the real control loop, closing current and voltage against the hardware, lives on the DC-DC board, not here. The Primary sequences; the Secondary regulates.

One number is still missing. F_MEAS, the measurement rate per circuit from the DC-DC boards, is undecided (Q-62). It sets the control cycle period, which every figure above depends on. Until it is fixed, this budget is provisional.

Shortest Path to a Reviewable Design

Suggested order of work

  1. Close AQ-1
    Confirm PREEMPT_RT in the NXP BSP; get the architect's call on A53 vs M7. Nothing else is stable until this settles.
  2. Close AQ-2
    Get F_MEAS from the Secondary team, fix the control cycle period, then redo BLK-12 with real numbers.
  3. Prototype the latency measurement
    A bare loop on the target hardware under synthetic best-effort load. About a day's work, and it either validates Option A or kills it early — which is exactly what you want from a day.
  4. Define the L2 / L3 interface
    Lets ICD work and execution-engine work proceed in parallel instead of in series.
  5. Review BLK-10 with hardware
    Especially AQ-5, the independent E-Stop path.
  6. Baseline the SAD and begin the SDD
